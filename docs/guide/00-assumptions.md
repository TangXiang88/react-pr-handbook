# 默认假设与降级

本手册是**强观点**路径：先给你一套可执行的默认做法，而不是列出所有流派。

## 默认假设

我们默认你所在团队接近「常见互联网小团队」：

| 假设 | 手册里怎么用 |
| --- | --- |
| GitHub + Pull Request | 分支、PR 模板、Review 流程按 GitHub 叙述 |
| CI 至少跑 lint / typecheck | 「开 PR 前先看 CI」；红了先修再求审 |
| 有 Figma（或等价设计稿） | 「设计还原」章要求对照稿面 |
| 有人做 Code Review | 合入前至少一人看过 |
| 可预览部署，或至少能本地截图 | PR 必须让人「看见」UI 变化 |

## 为什么要写死默认

初级前端最需要的是**第一条能走通的路**。选项过多会变成决策课，拖慢上手。每条硬规则旁会写一行「为什么」；若团队不同，用下面的降级，而不是整份手册作废。

## 降级对照

| 若没有… | 请改成… |
| --- | --- |
| 预览环境 | PR 描述里贴改动前后截图（同浏览器宽度） |
| Figma | 以产品/交互文字说明为准，并在 PR 写清「无设计稿，按 issue 验收」 |
| CI | 本地必须跑通 `npm run build`（或团队等价命令）再开 PR |
| 正式 Review 制度 | 至少找一位同事异步看一眼再合并 |
| GitHub（而是 GitLab 等） | 概念对齐即可：MR ≈ PR，流程章节仍适用 |

## 技术默认（示例仓库）

- React + Vite + TypeScript
- 目录：`pages/` + `features/` + `components/ui/`
- 示例是**教具**，不是生产模板；刻意做小
