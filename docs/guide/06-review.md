# 6. 评审与修改

> **主图位置：** `diagrams/06-review.svg`

![评审与修改](/diagrams/06-review.svg)

## 目标

把 Review 当成协作，而不是「被挑刺」。

## 默认做法

| 评论类型 | 你怎么做 |
| --- | --- |
| 必须改（bug / 规范 / 需求不符） | 改代码 + 回复已处理 |
| 建议（可讨论） | 采纳或简短说明不采纳原因 |
| 提问 | 先回答，再决定是否改 |

推送修正后，**回复线程**，让评审人不用翻 diff 猜你有没有改。

**为什么要回复：** 异步协作里，沉默 = 状态不明，合并会被拖住。

## 回复话术（可直接改）

- 必须改：`已按评论改到 <文件/行为>，请再看一眼。`  
- 采纳建议：`说得对，已改成 …`  
- 不采纳：`这次想保持现状，因为 …；如果合并后要统一风格可以另开 PR。`  
- 提问：`验收标准是 …；所以这里选择了 …`

## 自学时怎么练

没有真人评审时：

1. 自己用 PR 模板当检查表再扫一遍 diff  
2. 故意留一个小问题 → 自己提一条评论 → 再修并回复（练闭环）  
3. 或请同事只花 5 分钟看截图与描述是否「不用猜」

## 检查清单

- [ ] 每条「必须改」都有对应 commit 或明确说明
- [ ] 相关线程已回复，不是只 push 不说话
- [ ] CI 在最新 commit 上仍是绿的
